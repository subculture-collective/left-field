# FEC Receipt-Cutoff Publication Implementation Plan

> **For agentic workers:** Execute this plan task-by-task. Recommended path:
> dispatch a fresh subagent per task, review each result with `review-quality`,
> then continue. For complex multi-agent splits, use
> `parallel-feature-development`, `team-composition-patterns`, and
> `team-communication-protocols`. Steps use checkbox (`- [ ]`) syntax for
> tracking.

**Goal:** Produce reviewable nationwide FEC finance evidence bounded by FEC receipt date `2026-07-18`, including exact-election Schedule E aggregates only where evidence closes, without retaining contributor, payee, address, signer, or contact PII.

**Architecture:** Preserve the complete FEC v1 path and add one source-lock-bound v2 acquisition service shared by the standard ingest CLI and the operator CLI. The service uses isolated `fec_v2_*` evidence, run, signature, and proof tables; it performs stable nationwide filing enumeration, transient raw-file hashing and exact allowlisted sanitization, replayable canonical artifact storage, and typed closure. Publication requires independent detached review signatures and a network-free finalizer.

**Tech Stack:** TypeScript 5, Node.js Web Streams/Fetch, Vitest, PostgreSQL/Drizzle, OpenFEC v1, FEC electronic filing format, S3-compatible MinIO, and Ed25519 detached signatures.

**Release claim (exact):** **“FEC receipt-date-bounded through 2026-07-18, retrieved on `<timestamp>`.”** It is not “the OpenFEC database exactly as it appeared on 2026-07-18.”

**Compatibility rule:** This is additive v2 work. Existing FEC v1 envelopes, bytes, decoders, source URNs, object keys, receipt semantics, rows, and releases remain readable and byte-for-byte unchanged.

## Non-negotiable evidence and privacy semantics

- The nationwide universe is every applicable F3, F3X, F24, and F5 filing received on or before the cutoff, not just filings for already-authorized candidate committees. A filing that is unavailable, paper, unsupported, or malformed is globally blocking unless alternate **sanitized** evidence deterministically scopes it outside all candidate targets.
- The official historical source is OpenFEC `/v1/filings/` for enumeration and its returned `fec_url` for electronic bytes. Accept that URL only when it is HTTPS, its host is exactly `docquery.fec.gov`, and its path is exactly `/dcdev/posted/{the same FILE_NUMBER}.fec`; never synthesize a missing URL. Use the API credential only for `api.open.fec.gov`; never send a credential, API-key query parameter, or API-key header to docquery.
- For raw filing retrieval send `Accept-Encoding: identity`, use `redirect: "error"`, reject any redirect or `Content-Encoding` other than absent/`identity`, and accept only observed/policy-locked `application/octet-stream`, `binary/octet-stream`, or `text/plain` media types. Parse the file as bytes: delimiters, record identifiers, numeric/date fields, and IDs must be ASCII; do not decode or retain unallowlisted free text, so no whole-file UTF-8 assumption is made. The upstream SHA-256 is over the exact HTTP entity byte sequence received after transfer framing (which must be identity encoded), before record parsing; it is not an object key and is not replayable storage.
- Raw bytes are processed transiently in the isolated acquisition process, hashed while streamed, then discarded. They are never written to disk, object storage, logs, errors, APM, quarantine, fixtures, or snapshots. The operator already has the credential and MinIO and has approved this transient processing; reusable code must still preflight rather than assume either succeeds.
- V2 never reuses `finance_launch_receipts`, deletion attestations, the v1 proof path, or `ingest_runs`. It uses only isolated `fec_v2_*` evidence/run/signature/proof tables and mutually exclusive V1/V2 publication routing.
- Sanitization is an exact allowlisted projection, not a recursive denylist. Filer-controlled transaction and back-reference IDs are length-bounded and SHA-256 hashed with a domain prefix; no free text is retained. Canary/forbidden-key scans remain defense in depth.
- Missing evidence is never zero. `complete_zero` means a complete closure with no retained transactions; every unavailable or unresolved condition has a typed missing outcome.

## Actions required from the operator

1. Keep the existing OpenFEC/API.data.gov credential private in `FEC_API_CREDENTIAL`; do not paste it into chat, JSON, shell history, logs, or repository files.
2. Configure the already available MinIO/S3-compatible store with a versioned bucket, restricted credentials, and a tested immutable/version return contract. `RAW_OBJECT_ROOT` is local/nonproduction only.
3. Maintain approval for transient processing of public electronic filings; raw bytes are streamed and discarded and only hashes and sanitized artifacts remain.
4. Obtain the documented data-use/privacy disposition before changing a FEC source snapshot from `restricted` to `approved`.
5. Designate different people and different Ed25519 public-key fingerprints for `data_reviewer` and `release_approver`; keep private keys offline.
6. Review generated exceptions: candidate/committee mappings, special-election codes, unavailable/paper filings, malformed files, and ambiguous F24/F3X pairs.
7. Sign and import data-review payloads offline before finalization; construct, sign, and import publication approval only after the finalized payload exists. The application never accepts a private key.
